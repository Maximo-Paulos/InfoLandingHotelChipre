# Guía digital del huésped · Hotel Chipre

Landing para celular: el huésped escanea un QR (o recibe el link por WhatsApp) y tiene a mano check-in, Wi-Fi, emergencias, normas, preguntas frecuentes, dónde comer y qué hacer cerca.

El contenido vive en una base de datos **Supabase**. El dueño lo edita desde un **panel** que es un clon de la guía, con una caja debajo de cada texto; lo que guarda se ve enseguida en la guía de los huéspedes. Todo se publica en **Vercel**: no hay servidor propio.

```
Huésped → guía (React, Vercel) ──lee──▶ Supabase ◀──guarda con clave── panel del dueño (#/admin)
```

## Cómo edita el dueño
1. Entrar a `/#/admin` con la clave y tocar **Editar landing page** (el otro botón, **Ver huéspedes**, es del check-in digital: ver más abajo).
2. Navegar la guía como lo haría un huésped. Debajo de cada texto, botón, teléfono o link hay una caja para cambiarlo, y el cambio se ve al instante.
3. En las listas (pasos, normas, preguntas, lugares, teléfonos…) hay botones **Agregar** y **Quitar**.
4. Los datos que no se ven como texto (WhatsApp, teléfonos, link del mapa, Wi-Fi, horarios, links de reseñas) y el **cambio de la clave** están en **Datos generales**, el último botón del menú.
5. **Guardar cambios** los manda a la base. **Descartar** vuelve a lo último guardado. La base conserva las últimas 20 versiones.

Los íconos y el orden de las pantallas no se editan desde el panel. Cada pantalla tiene su link directo para los QR: `/#/wifi`, `/#/emergencias`, `/#/checkin`, `/#/checkout`…
**A dónde lleva cada botón** también se cambia desde el panel, debajo del botón o del lugar:
   - Botones de WhatsApp: "Número de WhatsApp de este botón". Vacío = usa el número general (Datos generales). Con número = ese botón escribe a otro WhatsApp.
   - "Cómo llegar" y "Ver hospital": "Link de Google Maps de este botón". Vacío = se arma solo.
   - Cada lugar (dónde comer, qué hacer, compras): "Link de Google Maps de este lugar". Vacío = busca por nombre.
   - Reseñas, lista de mapa y teléfono de recepción: su link o número está en la caja del botón.

## Check-in digital
El huésped carga sus datos antes de llegar (o en el mostrador) con un **código de 6 números** que le da recepción, y recepción ve la planilla. No reemplaza al QR: la guía sigue igual y el check-in es **un botón más**, abajo de todo, que solo aparece cuando lo encendés.

```
Huésped ─ código de 6 números ─▶ formulario ─▶ "¡Check-in realizado!" ─▶ vuelve al menú
Recepción (#/recepcion): ve el código (cambia solo) y la planilla · corrige datos y carga la habitación por 10 min
Admin (#/admin): Editar landing page · Ver huéspedes (todos, config, Drive, historial)
Foto del documento: celular ─▶ script de Google (tu cuenta) ─▶ carpeta de tu Drive   (en la base solo queda el id y el nombre)
                    la manda el huésped, o la carga a mano el dueño (agregar otra, quitar la que no se ve)
```

| Link | Para quién | Qué hace |
|---|---|---|
| `/#/registro` | huésped | pide el código y muestra el formulario (el botón del menú lleva acá) |
| `/#/entrar` | todo el personal | una sola pantalla de ingreso: la clave del dueño abre su panel y la de recepción abre recepción · se instala como app |
| `/#/recepcion` | recepción | clave propia · código con cuenta regresiva y usos · planilla de los últimos días · edición |
| `/#/admin` | dueño | inicio con dos botones |
| `/#/admin/editar` | dueño | el editor de la guía de siempre (los links viejos, como `/#/admin/wifi`, siguen andando) |
| `/#/admin/huespedes` | dueño | todos los huéspedes con búsqueda, configuración, conexión con Drive e historial de cambios |

### Cómo se enciende
1. **Base de datos** (una sola vez por proyecto de Supabase): ejecutar `supabase/checkin.sql` en el SQL Editor, después de `schema.sql`. Solo agrega tablas y funciones nuevas.
2. **Admin → Ver huéspedes → Configuración del check-in**: poner *Check-in digital* en **Encendido** y guardar. Mientras esté **Apagado** el botón no aparece y los códigos no funcionan.
3. **Clave de recepción** (misma pantalla, mínimo 8 caracteres). Solo el admin general la puede cambiar. Se guarda como hash, nunca en texto.
4. **Fotos** (opcional): *Conectar Drive para las fotos*, un asistente de 4 pasos (ver abajo). Hasta que lo conectes, el área de foto no aparece y el resto funciona igual.

### Qué se puede configurar
| Opción | Valor inicial |
|---|---|
| Cada cuántos segundos cambia el código | 15 |
| Cuántas personas pueden usar el mismo código | 3 |
| Recepción puede editar a los huéspedes / por cuántos minutos | sí / 10 |
| Días de huéspedes que ve recepción | 3 |
| Foto del documento | opcional (también: obligatoria · no pedir) |

Otros valores quedan fijos en la base (`private.checkin_config`): el huésped tiene 30 minutos para completar el formulario desde que canjea el código.

### Foto del documento → Drive
- El celular achica la foto (máx. 1600 px, menos de 900 KB, sin los datos ocultos como la ubicación) y la manda a un **script de Google que corre en tu cuenta** (`apps-script/Codigo.gs`), que la guarda en **una carpeta de tu Drive** con el nombre `AAAA-MM-DD_HH-mm_Apellido_Nombre.jpg`. Ni la base ni Vercel guardan la imagen; la planilla muestra «Ver», que abre el archivo en Drive (la ve quien tenga acceso a esa carpeta).
- Se usa un script y no una «cuenta de servicio» de Google porque, con Gmail común, Google no deja subir a una carpeta personal con una cuenta de servicio (no tienen espacio propio). El script corre como vos, no necesita consola de Google Cloud ni tarjeta.
- El script solo acepta fotos con un **permiso firmado y de pocos minutos** que la base le da al huésped que canjeó un código (hasta 3 fotos por huésped); solo escribe en esa carpeta y no comparte ni borra nada.
- Conexión (una vez, unos 10 minutos): *Admin → Ver huéspedes → Conectar Drive para las fotos*: 1) crear la carpeta y pegar su link, 2) pegar en [script.google.com](https://script.google.com) el código que arma el asistente, 3) *Implementar → Aplicación web → ejecutar como yo → acceso: cualquier persona*, 4) pegar la URL que termina en `/exec` y tocar *Guardar y probar* (guarda un archivo de prueba en la carpeta).

### Fotos en celulares viejos y de poca memoria
Los huéspedes usan celulares económicos, viejos o de poco rendimiento. Un celular con poca memoria podía mostrar «memoria insuficiente» al elegir la foto y mandar al huésped de vuelta al principio del formulario. Hay tres causas y las tres están atendidas:

1. **Se reconstruía la foto entera en memoria** para achicarla, a 4 bytes por píxel (12 MP ≈ 50 MB, 50 MP ≈ 200 MB, 108 MP ≈ 430 MB) y el sistema cerraba la página.
   *Ahora* (`src/checkin/jpegReducido.js` y `comprimir.js`): los JPEG grandes (3200 px o más de lado, los de cualquier cámara de hoy) se decodifican **directo en su tamaño final**: cada bloque de 8×8 se reconstruye ya en 4×4, 2×2 o 1×1 píxeles, después se lleva a 1600 px, se acomoda según la orientación del celular y se pasa a colores en una sola pasada, y la memoria se devuelve apenas deja de hacer falta. Nunca existe la foto entera ni una copia de la foto achicada: la memoria extra ronda los **25 a 35 MB sin importar los megapíxeles** (antes, de 60 a 430 MB). Si la foto no es un JPEG común (PNG, JPEG progresivo, CMYK) o es chica, la abre el navegador como antes; ante cualquier duda también vuelve a ese camino. El resultado es el de siempre (máx. 1600 px, menos de 900 KB).
2. **Abrir la aplicación de cámara del celular** hace que el sistema, para darle memoria a la cámara, cierre el navegador que quedó en segundo plano: al volver la página arranca de nuevo y la foto se pierde.
   *Ahora* (`src/checkin/CamaraFoto.jsx`): «Sacar foto» usa **la cámara dentro de la propia página** (la imagen se ve en pantalla completa con un recuadro para encuadrar el documento y la foto se saca de un cuadro de 1280×720), así que el navegador nunca sale de primer plano. Si el navegador no tiene cámara web, el huésped no da el permiso o la cámara no responde (25 segundos), se le explica y se le ofrece **«Usar la cámara del celular»** (la de antes) o la galería; después no se insiste con la que falló. Si el celular tiene linterna, aparece el botón *Prender luz*. La cámara se apaga apenas se saca la foto, se cancela o se cierra la pantalla.
3. **Procesador lento**: el achicado trabaja de a ratos de 30 ms, así que la pantalla no se traba, y muestra **«Preparando la foto… 45 %»** con una barra de avance.

- **Si igual se cierra la página** (cámara abierta, selector de fotos o preparando la foto): al volver, el formulario sigue ahí con lo que había escrito, la pantalla se desliza sola hasta la foto y explica qué pasó y cómo seguir (sacar la foto con la cámara del celular, fuera de la página, y elegirla de la galería; o enviar sin foto si no es obligatoria). No gasta otro uso del código. Se sabe porque, mientras se elige o se prepara la foto, queda una marca en la pestaña (`sessionStorage`, vale 30 minutos como máximo) que se borra sola si todo sale bien o si el huésped cancela.
- También sirve para las fotos que sube el dueño desde el panel (usan la misma función de achicado).
- **Recomendación**: dejar la foto del documento en **Opcional** (*Admin → Ver huéspedes → Configuración*). Con «Obligatoria», un huésped cuyo celular no puede sacar la foto no puede terminar el check-in; con «Opcional» envía igual, recepción le saca el documento y el dueño la sube después desde el panel.
- **Medido** con Chromium simulando un celular viejo (pantalla de Moto G4, procesador 4 veces más lento, modo «equipo de gama baja» y un tope de memoria para todo el navegador): con la versión anterior al arreglo, una foto de 48 MP hacía que se cayera la página con un tope de 240 MB; ahora el navegador aguanta hasta con 190 MB una foto de 108 MP. Pruebas: `npm run test:fotos` y las secciones 14 y 15 del punta a punta (ver abajo).

### Medio de pago
Cada huésped tiene un **medio de pago** que carga recepción (junto con la habitación, en la misma ventana y durante el mismo tiempo de edición) o el admin. Se elige de una lista desplegable y se ve como una columna más de la planilla.

- **Lista inicial:** Efectivo, Transferencia, USD efectivo, PayPal, Link de pago y Otros.
- **El dueño la edita** en *Admin → Ver huéspedes → Medios de pago*: cambiar un nombre, **agregar** uno escribiendo su nombre y **quitar** los que no use. Los cambios los ve recepción enseguida, sin recargar.
- **Nunca queda vacío:** los huéspedes que ya estaban cargados quedaron en **Otros**, y los que se carguen de ahora en más también arrancan en Otros hasta que recepción elija. «Otros» no se puede quitar (sí cambiarle el nombre).
- **Quitar no borra nada:** el medio deja de ofrecerse, pero los huéspedes que ya lo tenían lo siguen mostrando (se ve en la lista de «Quitados» y se puede **volver a poner**). Cambiar el nombre de un medio cambia cómo se ve en todos los huéspedes que lo tienen, sin tocar sus registros.
- **Base de datos:** la tabla `private.medios_pago` y la columna `private.checkins.medio_pago_id`. Si la base ya tiene el check-in, ejecutar `supabase/medios_pago.sql` en el SQL Editor (solo agrega, no borra nada y se puede repetir); una base nueva se arma con `schema.sql` + `checkin.sql`, que ya lo incluye.

### Fotos del documento que carga el dueño
Si un huésped no mandó su foto (por ejemplo, la foto no era obligatoria), o la que mandó no se ve, **el dueño puede cargarla a mano**. Cada huésped puede tener **varias fotos** (hasta 10 a la vez).

- **Dónde:** *Admin → Ver huéspedes*, en la columna **Foto** de cada huésped: el botón **Agregar foto** (o **Fotos**, si ya tiene). Abre una ventana con sus fotos.
- **Agregar:** *Sacar foto* o *Elegir de la galería* (también sirve una foto que mandó recepción por WhatsApp), vista previa y *Subir esta foto*. Se achica en el dispositivo y va **directo al mismo script de Drive de siempre** (no hay que cambiar ni volver a publicar nada en Google), con el mismo nombre `AAAA-MM-DD_HH-mm_Apellido_Nombre.jpg`. Puede agregar todas las que quiera, aunque el huésped ya tenga una.
- **Quitar:** *Quitar* saca la foto de la lista (pregunta antes). **No borra nada**: el archivo sigue en tu Drive, la fila sigue en la base, aparece en *Quitadas* y se puede **volver a poner**. Si algún día querés borrarla del todo, se hace a mano en tu carpeta de Drive.
- **La planilla** (la del admin y la de recepción) muestra un link por cada foto activa: *Ver* si hay una, *Ver 1*, *Ver 2*… si hay varias. Recepción las mira y puede **agregar** la del huésped que no la subió (ver abajo); quitar es solo del dueño.
- **Historial de cambios:** queda anotado cuándo se agregó, quitó o volvió a poner una foto (sin el nombre del archivo, que lleva el nombre del huésped).
- **Base de datos:** la tabla `private.checkin_fotos` (las fotos de cada huésped; las que ya estaban pasan solas) y los permisos de pocos minutos `private.foto_permisos`. Si la base ya tiene el check-in y los medios de pago, ejecutar `supabase/fotos_admin.sql` en el SQL Editor (solo agrega, no borra nada y se puede repetir). **La guía y el script de Drive que ya están publicados siguen andando igual** antes y después de ejecutarlo: no cambia ninguna firma de función. Una base nueva se arma con `schema.sql` + `checkin.sql`, que ya lo incluye.
- **Recepción agrega la foto que falta:** en su planilla, cada huésped tiene *Agregar foto* (o *Fotos* si ya tiene). Es el mismo camino que el del dueño (permiso de 10 minutos, directo al script de Drive, sin tocar el script) y queda marcada como *La cargó recepción*. Recepción **no puede quitar ni cambiar** ninguna foto, tampoco la del huésped, y solo ve a los huéspedes de los días que muestra su planilla. Es el plan B cuando al huésped le falla la subida en su celular. Si la base ya tiene el check-in, los medios de pago y las fotos del dueño, ejecutar `supabase/fotos_recepcion.sql` en el SQL Editor (agrega 2 columnas y 2 funciones, no quita nada y se puede repetir); una base nueva se arma con `schema.sql` + `checkin.sql`, que ya lo incluye.

### Reglas importantes
- **Nada se borra**: no hay botones ni funciones que borren de verdad a huéspedes, reservas ni fotos. Lo que el dueño «elimina» (ver «Reservas abiertas… el dueño corrige, mueve y elimina») deja de verse y de contar, pero queda guardado y se restaura. Cuando Drive se llene, se pasa a mano a un disco.
- La **habitación** la carga solo recepción (dentro de la ventana de edición) o el admin. Pasada la ventana, solo el admin corrige.
- Los cambios de recepción y de admin quedan en el **historial** (quién, cuándo y qué campos, no los valores).
- Las tablas con datos de huéspedes están en el esquema `private`, sin acceso directo desde la API: se entra solo por funciones que verifican el código, la clave de recepción o la del admin, con freno por IP en los intentos fallidos.
- El formulario guarda la aceptación del huésped (casilla con link a Términos y condiciones) y cuándo la dio. El hotel es responsable de esos datos (Ley 25.326): conviene que un abogado revise el texto de aceptación, cuánto tiempo se conservan los datos y el hecho de que Supabase y Drive son servicios del exterior.
- Que un teléfono sea **válido** (largo y formato del país) no prueba que **exista** o sea del huésped; eso requeriría verificar por SMS o WhatsApp.
- **Derechos del huésped** (acceso, rectificación, supresión): el sistema no borra nada a propósito. Si un huésped pide que se borren sus datos, hoy se haría a mano desde Supabase y Drive; conviene definir con el abogado cuánto tiempo se conservan y cómo se atienden esos pedidos.
- Mientras el huésped completa el formulario, lo escrito se guarda en la pestaña de su navegador (para no perderlo si recarga o cambia de idioma). Se borra al enviar o al cerrar la pestaña.

#### Texto sugerido para los Términos y condiciones (borrador, que lo revise un abogado)
Se edita desde el panel (Términos y condiciones). Completá lo que está entre corchetes:
```
# Datos personales y check-in digital
Al completar el check-in digital el huésped nos brinda su nombre, apellido, email, teléfono, nacionalidad, localidad, domicilio, tipo y número de documento y una foto del documento. Usamos esos datos para registrar la estadía, cumplir con las obligaciones de registro de huéspedes y gestionar el alojamiento. Responsable de la base de datos: [razón social, CUIT, domicilio y email de contacto del hotel].
Los datos se guardan en servidores de Supabase y la foto del documento en Google Drive, ambos con sede en el exterior (Estados Unidos), bajo la responsabilidad del hotel. Solo accede el personal autorizado.
El huésped puede ejercer sus derechos de acceso, rectificación y supresión escribiendo a [email], salvo cuando el hotel deba conservar los datos por obligaciones legales.
La Agencia de Acceso a la Información Pública, en su carácter de Órgano de Control de la Ley N° 25.326, tiene la atribución de atender las denuncias y reclamos que interpongan quienes resulten afectados en sus derechos por incumplimiento de las normas vigentes en materia de protección de datos personales.
```

### Probarlo sin tocar la base real
```
npm run local
```
Levanta una base de prueba **en memoria** (con los mismos archivos SQL que producción) y la guía apuntando a ella, con el check-in prendido y un Drive simulado. Claves de prueba que muestra el comando. Lo que cargues ahí se pierde al cerrar.

Arranca con **datos inventados** (casi un año de reservas y unos 2.300 huéspedes de varios países, pagos en pesos y dólares) para ver las estadísticas llenas. `npm run local -- --vacio` arranca sin nada.

Pruebas automáticas (no usan la base real):
- `node scripts/test-validar.mjs`: reglas de validación del formulario (teléfonos, documentos, etc.).
- `node scripts/test-apps-script.mjs`: la lógica del script de Google con un Drive simulado.
- `node scripts/test-frenos.mjs`: los frenos de intentos (claves y código de 6 números) cuentan por la IP real y no se esquivan escribiendo un `X-Forwarded-For` falso.
- `node scripts/test-medios-pago.mjs`: arma una base como la de producción con huéspedes ya cargados, le aplica `supabase/medios_pago.sql` y comprueba que no se pierde nada (quedan en «Otros»), que se puede repetir y que queda idéntica a una base nueva; además prueba elegir, agregar, renombrar, quitar y volver a poner medios de pago.
- `node scripts/test-fotos-admin.mjs`: arma una base como la de producción con huéspedes con y sin foto, le aplica `supabase/fotos_admin.sql` y comprueba que no se pierde nada (las fotos que ya estaban pasan a la lista nueva), que se puede repetir sin resucitar una foto quitada y que queda idéntica a una base nueva; además prueba, con el script de Drive de siempre sin cambios, que el dueño suba, agregue otra, quite y vuelva a poner fotos, que nada se borre, los permisos (vencen y se gastan), el tope de 10 y que un anónimo no pueda tocar nada.
- `node scripts/test-fotos-recepcion.mjs`: arma una base como la de producción con fotos del huésped y del dueño, le aplica `supabase/fotos_recepcion.sql` y comprueba que no se pierde nada, que se puede repetir, que queda idéntica a una base nueva y que recepción ve y agrega fotos pero no puede quitar ninguna.
- `node scripts/test-sesiones.mjs`: arma una base como la de producción, le aplica `supabase/sesiones.sql` y comprueba que no se pierde nada, que se puede repetir, que queda idéntica a una base nueva, y que cada código de dispositivo sirve solo para lo que le toca, vence, se renueva y se puede cerrar; también que un código no puede cambiar la clave del dueño.
- `node scripts/test-paginacion.mjs`: la lista de huéspedes del admin se pide de a 50 («Cargar más»): con 120 huéspedes comprueba que cada tanda sigue justo donde terminó la anterior, sin repetir ni saltear a nadie, también con búsqueda. La pantalla se prueba en la sección 12 del punta a punta.
- `node scripts/test-jpeg-reducido.mjs` (o `npm run test:fotos`): el achicado de las fotos. Compara el decodificador liviano contra Chrome (escalas 8/8, 4/8, 2/8 y 1/8; formatos de color 4:4:4, 4:2:2, 4:2:0 y gris; tablas de Huffman estándar y propias; marcadores de reinicio; tamaños que no son múltiplos de 8; las 8 orientaciones de EXIF; la foto ya terminada en su tamaño final y el aviso de avance), comprueba que con lo que no entiende (progresivo, CMYK, PNG, archivos cortados o rotos, cabeceras que mienten) devuelve «nada» y se usa el camino de antes, y prueba en el navegador una foto de 12 MP en las 8 orientaciones, una panorámica, una imagen imposible de comprimir, un PNG y los errores. Las fotos de prueba chicas están en `scripts/fixtures/jpeg/` (`generar.py` las rehace); las grandes se arman en la propia prueba (`scripts/fotos-ayuda.mjs`). Requiere Playwright y Chromium, igual que el punta a punta.
- `node scripts/e2e-checkin.mjs`: punta a punta con navegador (huésped y recepción a la vez). Requiere Playwright (`npm i -D playwright`) y Chromium; `CAPTURAS=carpeta` guarda capturas de cada pantalla. La sección 14 prueba una foto de 12 MP por el formulario real y el caso de la página que se cierra por falta de memoria; la 15, la cámara dentro de la página con una cámara simulada (`scripts/fixtures/camara/documento.mjpeg`: un documento con un cuadrado de color en cada esquina; `generar.py` la rehace): sacar la foto, cancelar, cierre de la página con la cámara abierta, sin permiso, navegador sin cámara web y cámara que no responde.

## Probarlo en tu laptop
Necesita [Node 20 o superior](https://nodejs.org) y Git.
```
git clone https://github.com/Maximo-Paulos/InfoLandingHotelChipre.git
cd InfoLandingHotelChipre
npm install
npm run dev
```
Abrí http://localhost:5173 (guía) y http://localhost:5173/#/admin (panel). Usa la misma base de Supabase que la versión publicada, así que lo que guardes en el panel **cambia la guía real**.

Para verla desde el celular en la misma red Wi-Fi: `npm run dev -- --host` y abrir `http://IP-DE-TU-LAPTOP:5173`.

## App del personal: ingreso único, sesión en el dispositivo e instalable
- **Un solo ingreso:** `/#/entrar`. La clave del dueño (también la del codueño, que comparte esa clave) abre el panel; la de recepción abre recepción. Si el dispositivo ya tiene la sesión abierta, entra directo.
- **Sesión por dispositivo:** al poner la clave, la base le da al teléfono un código al azar (`sd_…`) que dura **60 días de uso** (se renueva cada vez que se usa). En el teléfono se guarda solo ese código; **la clave no se guarda en ningún lado**, y en la base solo queda la huella (sha256) del código.
- **El dueño también entra a recepción** con su sesión (en su inicio hay *Ver recepción* y, dentro, *Panel del dueño* para volver). Recepción no puede entrar al panel del dueño.
- **Cerrar sesiones:** *Salir* cierra la de ese dispositivo. En el inicio del panel, *Dispositivos con sesión abierta* lista cada celular o compu (con el nombre, el rol y el último uso) y permite **cerrar uno** o **cerrar en todos los demás**. Si se pierde un teléfono, es lo primero que hay que hacer. Nada se borra: la sesión queda marcada como cerrada.
- **Cambiar claves cierra sesiones:** al cambiar la clave del dueño se cierran las sesiones de los dispositivos del dueño; al cambiar la de recepción, las de recepción. Cambiar la clave del dueño **pide la clave actual de verdad**: un celular que quedó abierto no la puede cambiar.
- **Moverse sin perderse:** todas las pantallas del personal tienen arriba una barra fija con una **flecha para volver** (a *Inicio*), el nombre de la pantalla y el botón **Menú** (las tres barritas), que abre la lista de pantallas (Inicio, Huéspedes, Recepción, Editar la guía), la guía como la ve el huésped y *Salir*. Recepción solo ve lo suyo. El editor de la guía avisa si hay cambios sin guardar antes de salir.
- **Huéspedes en el celular:** cada huésped es una **tarjeta** (nombre, habitación, pago, documento, teléfono, foto y *Editar*), sin tener que deslizar hacia los costados; en la compu sigue siendo la tabla completa. En *Huéspedes* primero está la lista y abajo los *Ajustes* (cerrados hasta que se tocan).
- **Instalar como app (sin App Store ni Google Play):** desde `/#/entrar`. En Android o la compu aparece el botón *Instalar la app*; en iPhone, desde Safari: *Compartir → Añadir a pantalla de inicio*. Queda con el ícono del llavero y abre a pantalla completa en el ingreso. La guía de los huéspedes **no** ofrece instalarse.
- **Sin copia sin conexión a propósito:** la app no guarda datos de huéspedes en el teléfono (solo el código de dispositivo). Los íconos están en `public/iconos/` y el manifiesto en `public/personal.webmanifest`.
- **Base de datos:** la tabla `private.sesiones` y 5 funciones nuevas. Si la base ya tiene el check-in, los medios de pago y las fotos, ejecutar `supabase/sesiones.sql` en el SQL Editor (solo agrega, no quita nada y se puede repetir). **Ejecutarlo ANTES de publicar la versión nueva de la guía**: sin esas funciones el ingreso nuevo no anda. Una base nueva se arma con `schema.sql` + `checkin.sql`, que ya lo incluyen.

## Equipo, pestañas de abajo y «habilitado por»
- **Una clave por persona:** en la pestaña **Equipo** (solo el dueño) se agrega a cada persona con un **nombre (alias)**, un rol (*Recepción* o *Dueño*, este último entra a todo menos a Equipo) y su propia clave. Solo el dueño pone y cambia las claves; no se pueden ver después, solo cambiar. Dos personas no pueden tener la misma clave ni el mismo nombre activo. Dar de baja cierra sus sesiones y deja de servir su clave y su código; nada se borra.
- **Un código por persona:** cada una ve el suyo arriba de *Reservas*, apenas crea una reserva o le da código a una. Cuando un huésped lo usa, el check-in queda anotado como **«Habilitó: nombre»** (en la planilla de recepción y en la del dueño). Ese nombre se guarda como texto **tal como se llamaba ese día**: si Jorge se va y le cambian el nombre y la clave a Lucas, los check-ins viejos siguen diciendo Jorge y los nuevos dicen Lucas. Los check-ins anteriores a esta versión quedan sin «habilitó».
- **Pestañas abajo, como una app:** recepción tiene *Reservas* y *Huéspedes*; el dueño, *Inicio*, *Reservas*, *Huéspedes* y *Datos*; todos tienen *Más* (para el dueño: Equipo, Ajustes, editar la guía; para todos: ver la guía del huésped y salir). Máximo 5 pestañas, como una app del celular. Arriba se ve el nombre de la pantalla y quién entró.
- **Base de datos:** ejecutar `supabase/equipo.sql` en el SQL Editor (solo agrega tablas y columnas, pasa la clave de recepción de hoy a la persona «Recepción» sin que nadie tenga que volver a entrar, no quita nada y se puede repetir). **Ejecutarlo ANTES de publicar la versión nueva.** Una base nueva se arma con `schema.sql` + `checkin.sql`.
- `node scripts/test-equipo.mjs`: migración desde la base de hoy (sin perder nada, repetible, idéntica a una base nueva) y todo el flujo: crear personas, claves únicas, quién puede tocar al equipo, un código por persona, el alias congelado en cada check-in, dar de baja y seguridad.

## Reservas por habitación, año de nacimiento y estadísticas
- **Reserva antes del código:** en *Reservas*, recepción (o el dueño) abre una **reserva**: habitación, **valor total** de la habitación, moneda (ARS/USD), si dejó una **seña** (y cuánto pagó en el hotel), medio de pago y fecha del cobro. **Sin reserva no hay código.** Todos los huéspedes que hagan el check-in con los códigos de esa reserva quedan en la misma habitación, con su monto y medio de pago. Otra habitación = otra reserva (el código de la anterior deja de servir). Los códigos siguen cambiando cada pocos segundos mientras el código está a la vista; se apaga solo a los **10 minutos** (el dueño lo cambia en *Ajustes → Check-in*) o con *Volver a la lista*, pero **la reserva no se cierra**: ver «Reservas abiertas» más abajo. También hay *Dar 10 min más* y *Corregir reserva*.
- **Un monto por habitación**, no por persona. Cada reserva dice **cuántos huéspedes** se esperan (obligatorio) y ese número se controla: ver «Reservas abiertas».
- **Valor total, pago en el hotel y seña:** una habitación de 100.000 con 30.000 de seña se carga como *total 100.000* y *pagó en el hotel 70.000*; la seña (30.000) es la diferencia y, si se sabe, se carga también la fecha en que se cobró. Sin seña, se pagó todo en el hotel. Todo va en la misma moneda. Así la **tarifa promedio es la real** (con la seña incluida) y no solo lo que se cobró en el hotel; y para controlar la caja se ve cuánto cobró cada persona en el hotel, aparte de las señas.
- **Correcciones:** recepción corrige una reserva dentro de la ventana de edición de siempre; el dueño siempre. Cada cambio queda en el historial. Los check-ins de antes quedan «sin reserva» y el dueño los puede asignar a una desde la planilla.
- **El huésped informa su año de nacimiento** (obligatorio en el formulario; recepción puede dejarlo vacío al corregir un check-in viejo).
- **Se usa como una app en el celular:** las pantallas ocupan toda la pantalla, el título está solo en la barra de arriba y lo largo se acorta: *Huéspedes* es una lista por habitación y, al tocar a una persona, se abre su ficha (llamar, escribir por WhatsApp, editar, fotos); *Datos* se mira por secciones (Resumen, Ventas, Huéspedes, Operación) y el período se elige en una hoja que sube desde abajo; el *Inicio* del dueño muestra el día, el mes y los últimos check-ins; los *Ajustes* (check-in, medios de pago, Drive, historial, celulares con sesión) tienen su pantalla propia en *Más*. En la compu la planilla sigue siendo una tabla.
- **Pestaña Datos (estadísticas):** ingresos en dólares, habitaciones vendidas, tarifa promedio, ingreso por huésped, país de origen (torta), edades, ciudades, tamaño del grupo, días y horas de más movimiento, habitaciones que más se venden, medios de pago, quién cargó cada reserva, y cuántos dejaron email/teléfono o ya se habían alojado. Con período elegible (mes, 30 días, 3 meses, 12 meses, año, todo) y comparación con el período anterior. Cada gráfico trae «Ver números» con la tabla.
- **Dólar:** lo cobrado en pesos se pasa a dólares con el **dólar oficial (venta) del día de cada pago** (lo pagado en el hotel, con la fecha del cobro; la seña, con la fecha de la seña, o la del cobro si no se cargó), bajado de la API pública de ArgentinaDatos (solo lectura: no se le manda ningún dato del hotel). Si no responde, los pesos quedan fuera de los totales en dólares y la pantalla lo avisa. El monto se guarda siempre en su moneda original.
- **Privacidad:** la base le entrega a la pantalla de estadísticas solo cifras sueltas: nunca nombres, documentos, emails, teléfonos ni domicilios.
- **Base de datos:** ejecutar `supabase/estadias.sql` en el SQL Editor **después de `checkin.sql`** (agrega una tabla, algunas columnas y funciones nuevas, no borra nada y se puede repetir; vale igual para una base nueva; las reservas que ya tuviera quedan como cobradas enteras en el hotel). **Ejecutarlo ANTES de publicar la versión nueva de la guía**: con la versión nueva y sin esas funciones no hay forma de sacar un código. Los códigos que estén circulando dejan de servir hasta que recepción abra una reserva.
- `node scripts/test-estadias.mjs`: reservas (validaciones, huéspedes agrupados, código nuevo al abrir otra, cierre y vencimiento, correcciones y auditoría, check-ins viejos). `node scripts/test-estadisticas.mjs`: la función de estadísticas (solo el dueño, sin datos personales) y las cuentas de la pantalla (dólar del día, períodos, series, torta, edades). `scripts/e2e-checkin.mjs` todavía no contempla las reservas. `node scripts/test-reservas-abiertas.mjs`: ver «Reservas abiertas».

## Noches, canal de venta, categoría y caja
- **Cada reserva** lleva la cantidad de **noches**, su **canal de venta** y su **categoría** de habitación. Con las noches la guía saca la **tarifa por noche** y el **ticket promedio** (lo que deja una reserva que cobra); al cargar el valor total, el formulario muestra cuánto sale por noche para que recepción vea si se equivocó.
- **Canales y categorías** son dos listas que el dueño edita en *Más > Ajustes* (como los medios de pago: nada se borra, lo quitado deja de ofrecerse). Vienen con Directo, Obra social, Agencia y Online, y Single, Doble, Triple y Cuádruple.
- **Obra social (canal «sin cobro»):** no lleva monto ni medio de pago (se factura aparte). Cuenta en habitaciones vendidas, noches, edades y países, pero **no** en ingresos, tarifa promedio, medios de pago ni señas. Un canal no puede cambiar si cobra o no cuando ya tiene reservas.
- **Caja** (*Datos > Caja*, o «Ver cobros y reservas» en Inicio): las reservas del período **con huéspedes** (las que suman). Las que todavía no tienen ningún check-in no suman: se ven aparte, en *Sin huéspedes todavía* (ver «Reservas abiertas»). Cada una con fecha, habitación, categoría, noches, canal, total, seña, lo pagado en el hotel, medio de pago y quién la cargó; tocarla la abre para corregirla. Arriba, los totales por moneda (pesos y dólares sin mezclar) y por medio de pago.
- **Base de datos:** volver a ejecutar `supabase/estadias.sql` en el SQL Editor (no borra datos; las reservas que ya había quedan en el canal «Directo», sin noches ni categoría hasta que se corrijan). **Ejecutarlo ANTES de publicar la guía nueva**, y la guía vieja ya no puede corregir reservas (pide noches). Antes conviene copiar las tablas con `docs/respaldo-antes-de-estadias.sql` (cambiando el nombre del esquema si ya existe uno de otro día).
- Prueba: `node scripts/test-estadias.mjs` arma una base como la publicada hoy (`scripts/fixtures/estadias-v1.sql`), le aplica el archivo nuevo dos veces y comprueba que las reservas quedan idénticas.

## Reservas abiertas: cantidad de huéspedes, reservas en espera y anular
Antes, una reserva cargada «de prueba» (o a la que al final no llegó nadie) seguía sumando en las estadísticas y no se encontraba en ningún lado (no tenía huéspedes, y la lista era de huéspedes). Y como el código se apagaba a los 10 minutos, el huésped que llegaba más tarde que el resto no tenía cómo entrar a su habitación. Ahora:

- **Todo es obligatorio para abrir una reserva**, incluida la **cantidad de huéspedes** (de 1 a 12): habitación, categoría, noches, canal de venta, monto (si el canal cobra), medio de pago y fecha. Sin eso no sale ningún código. Lo controla la base, no solo la pantalla.
- **Una reserva sin ningún huésped NO suma en nada**: ni en ingresos, ni en habitaciones vendidas, noches, tarifas, medios de pago ni en la caja. Está «en espera». Apenas entra el primer huésped, empieza a contar (con su monto completo, que es por habitación).
- **Reservas abiertas** (pestañas *Faltan llegar* y *Falta cerrar* de *Reservas*): una reserva sigue abierta mientras le falten huéspedes por hacer el check-in, aunque el código ya se haya apagado. La lista es de **todo el equipo**: si Lucía abrió la reserva a la mañana, Martín a la tarde toca *Dar código* y el huésped que llegó tarde entra a la misma habitación (el check-in dice «Habilitó: Martín»). Cada reserva muestra «1 de 3 huéspedes» y quiénes ya entraron.
- **Se cierra sola** cuando entra el último huésped: el código deja de servir y de verse, y desaparece de la lista de recepción. Si alguien llena el formulario mientras la habitación se completa con otro, la base lo rechaza (la fila de la reserva se bloquea al enviar, así dos huéspedes no se quedan con el mismo último lugar) y el huésped ve «Esta habitación ya tiene registrados a todos sus huéspedes… Consultá en recepción».
- **Solo el dueño la reabre**: pasada la ventana de edición, recepción no puede corregir una reserva. El dueño sube la cantidad de huéspedes (*Datos → Caja* o *Huéspedes* → *Corregir* en la reserva) y la reserva vuelve a estar abierta y a verse en recepción. También puede darle código él mismo (*Dar código a los que faltan*, en la caja).
- **El dueño corrige, mueve y elimina** (todo en *Huéspedes* y en *Datos → Caja*; recepción no puede nada de esto):
  - **Corregir una reserva**: habitación, categoría, noches, **cantidad de huéspedes**, canal, monto, seña, medio de pago y fecha, siempre (recepción solo los primeros minutos). Subir la cantidad reabre la reserva; bajarla hasta los que ya entraron la cierra.
  - **Mover a un huésped a otra reserva** (o *Dejar sin reserva*): en su ficha, *Mover a otra reserva*. Sirve cuando recepción lo puso en la habitación equivocada. La reserva que deja pierde uno (si le falta gente, vuelve a estar abierta) y la que recibe toma su habitación; también se puede mover a una reserva que todavía no tiene a nadie. No se puede mover a una reserva eliminada.
  - **Eliminar a un huésped** (*Editar datos → Eliminar huésped*): deja de verse en todas las listas y no cuenta en ninguna estadística (tampoco como «visita» repetida). A su reserva le falta uno: si estaba completa, vuelve a estar abierta para cargar al que corresponde.
  - **Eliminar una reserva**, también con huéspedes (*Corregir reserva → Eliminar reserva*, en *Huéspedes* o en la caja): la reserva y todos sus huéspedes dejan de verse y de contar. Si se restaura, vuelven con ella los que se eliminaron junto con ella; los que ya se habían eliminado por separado siguen eliminados.
  - **Restaurar**: huéspedes en *Huéspedes → Huéspedes eliminados*; reservas en *Datos → Caja → Reservas anuladas*.
  - **No se borra nada**: «eliminar» marca la fila con quién y cuándo (`quitado_en`, `quitado_por` / `anulada_en`, `anulada_por`) y todo queda en el historial. Es la regla «nada se borra» del proyecto (son datos de huéspedes, un registro). Borrar de verdad, si hiciera falta, se hace a mano en Supabase. La base lee a los huéspedes por la vista `private.checkins_activos`: toda lista o cuenta nueva tiene que usarla, no la tabla.
- **A los 3 días desaparece de recepción** (el mismo plazo que ya tienen los huéspedes: *Días de huéspedes que ve recepción*). Se cuenta desde la última actividad: cuando se cargó, cuando entró el último huésped o cuando el dueño la reabrió. Una reserva con huéspedes sigue contando en las estadísticas; una en espera nunca. El dueño la sigue viendo en la caja y puede darle código desde recepción.
- **Anular** (*Anular* en la lista de recepción): solo una reserva **sin huéspedes**, y solo las que recepción ve. No se borra nada: la fila queda marcada con quién y cuándo y el código se apaga. Recepción no puede anular una reserva con huéspedes: son personas registradas. El dueño sí puede eliminar cualquiera (ver abajo) y es el único que **restaura** (*Datos → Caja → Reservas anuladas*).
- **El dueño las encuentra**: en *Inicio* aparece un aviso («2 reservas sin huéspedes. No suman en las cifras») y en *Datos → Caja* el bloque **Sin huéspedes todavía**, con *Anular* en cada una.
- **Base de datos:** volver a ejecutar `supabase/estadias.sql` en el SQL Editor (no borra datos y se puede repetir). Las reservas que ya había quedan «completas» (tantos huéspedes esperados como check-ins tenían); **las que no tenían ningún check-in (por ejemplo, las de prueba) dejan de sumar y aparecen en *Sin huéspedes todavía*** para anularlas. **Ejecutarlo ANTES de publicar la guía nueva**: la guía vieja no puede abrir reservas sin la cantidad de huéspedes, y la nueva no funciona sin el SQL.
- Pruebas: `node scripts/test-quitar.mjs` (corregir la cantidad, mover, eliminar y restaurar huéspedes y reservas, que lo eliminado no cuente en ninguna lista ni estadística, y la migración). `node scripts/test-reservas-abiertas.mjs` (cantidad obligatoria, en espera, huéspedes a destiempo con otra persona del equipo, cierre automático, tope al enviar, anular y restaurar, 3 días, reabrir y la migración desde la versión publicada hoy, `scripts/fixtures/estadias-v2.sql`, con reservas de prueba sin huéspedes).

## Reservas anotadas: cargar las llegadas por adelantado
En vez de dejarle anotadas las reservas futuras a recepción, **el dueño las carga en la app** y recepción las ve con todo lo que necesita saber, cuánto cobrar incluido.

- **Quién puede qué:** el **dueño** anota, corrige y **cancela** (en *Más → Reservas anotadas*, o el botón *Anotar una reserva por adelantado* del Inicio, que también muestra las próximas llegadas). **Recepción anota y corrige, pero no cancela**: en *Reservas* tiene *Anotar una reserva (a nombre de…)* y *Corregir los datos de la reserva* en cada llegada, y no hay ningún botón de cancelar (si una no tiene que existir, le avisa al dueño). Recepción corrige las llegadas que ve (las de los próximos y últimos 3 días, igual que para hacer el check-in); el dueño, cualquiera. Todo queda en el historial con quién lo hizo y qué campos tocó.
- **El que llega de la calle sin reserva:** recepción lo anota a su nombre y con el monto (*Anotar una reserva*; arranca con la fecha de hoy) y, como llega hoy, al guardar **se abre solo el check-in** de esa reserva: elige cómo paga y genera el código, igual que con las que cargó el dueño. *Nueva reserva rápida (sin nombre)* sigue existiendo para cargar la reserva y el cobro de una vez, sin nombre.
- **Qué lleva cada una:** **a nombre de** quién está (el titular), **fecha de ingreso**, noches, habitación, categoría, canal, **cantidad de huéspedes**, los **precios** y la **seña** que ya pagó, y una **nota** para recepción (horario de llegada, pedidos…).
- **Precios:** precio en **efectivo** (pesos), precio en **transferencia** (opcional: sin cargar se cobra igual que en efectivo) y precio en **dólares** (opcional: sin cargar se calcula con el dólar oficial de hoy). La **seña** (en pesos) no importa cómo se pagó: se descuenta de lo que resta en cualquier forma de pago. La seña no puede pasar del precio más bajo.
- **Cuánto hay que cobrar** (se ve al anotar y en la tarjeta de recepción): lo que resta es el precio de cada forma menos la seña. Ejemplo: efectivo 100.000, transferencia 110.000 y seña 30.000 → **efectivo 70.000, transferencia 80.000**. En **dólares**: con precio en dólares, ese precio menos la seña pasada a dólares; sin precio en dólares, **lo que resta en efectivo dividido por el dólar oficial (venta) de hoy** (se marca con * como estimado). Si no se puede traer el dólar oficial, no se inventa: dice «sin cotización» y se escribe a mano. Las cuentas están en `src/checkin/cobro.js` (`node scripts/test-cobro.mjs`).
- **La pantalla «Reservas» (reemplaza a «Código»).** Es la pestaña de abajo donde pasa todo lo de las reservas; ya no hay una pestaña «Código» aparte: el código para el huésped aparece **arriba, dentro de Reservas**, apenas se crea una reserva o se le da código a una (con *Ocultar el código*, *Código nuevo ahora*, *Dar N min más*, *Corregir reserva*, *Cerrar reserva* y *Anular*). De arriba para abajo:
  - **Cartel de llegadas** (para saber si hay que estar atento): *«Faltan llegar 3 reservas»* con cuántas son de hoy, atrasadas o con el código dado y nadie adentro, y **a quién esperar**; o *«Ya llegaron todas las de hoy · Podés quedarte tranquilo»* (con cuántas llegan mañana). No cambia con el buscador.
  - **Para crear:** *Anotar reserva (con nombre)* (a nombre de alguien, con precios y seña; el que llega de la calle) y *Reserva rápida (sin nombre)* (habitación, noches, huéspedes y cobro de una vez).
  - **Buscador** por nombre, habitación o nombre de quien ya ingresó, que filtra todas las pestañas.
  - **Pestañas de arriba** (como en Estadísticas), cada una con su cantidad: **Faltan llegar** (las de hoy y atrasadas que no empezaron el check-in, y las que tienen el código dado y nadie adentro; se les hace el check-in, *Dar código* o *Anular*) · **Falta cerrar** (ya ingresó alguien y faltan otros: *Dar código* al que falta o **Cerrar reserva**) · **Cerradas** (entraron todos, o se cerraron a mano con menos de los esperados; el dueño puede **Reabrir**) · **Próximas** (llegan de mañana en adelante, por día) · **Historial** (las que ya llegaron, **por día**, con cuántas reservas y huéspedes entraron cada día).
  - **Cerrar una reserva a mano:** si se anotaron dos y vino uno, y «al final no viene el otro», recepción toca *Cerrar reserva* (pide confirmación): la reserva queda **cerrada** («Cerrada con 1 de 2 · por Recepción»), deja de esperar al que falta y su código deja de servir. Sin ningún huésped no se cierra: se anula. **Solo el dueño la reabre** (*Reabrir*, en *Cerradas*). Las estadísticas no cambian: sigue siendo una reserva con los huéspedes que ingresaron.
  - **Qué ve recepción:** solo los días que fija el dueño (N atrás y N adelante); lo que queda fuera no aparece ni buscando. El dueño ve todo (hasta 60 días atrás en las ya empezadas).
- **Recepción: pestaña «Reservas» (próximas reservas).** Lista las reservas anotadas que llegan de **N días atrás a N días adelante** (N = «Días que ve recepción, hacia atrás y hacia adelante», en *Ajustes → Configuración del check-in*; el dueño lo cambia, por ejemplo a 5), de la más cercana a la más lejana y agrupadas por día (*Hoy*, *Mañana*, *En 2 días*…), con un **buscador** por nombre, habitación, nota, canal o categoría (sin importar mayúsculas ni tildes; «perez 107» encuentra a Juan Pérez de la 107). **Lo que queda fuera de esos días recepción no lo ve ni lo encuentra buscando** (con 5: una reserva de hace 7 días o de dentro de 7 no aparece, y la pantalla lo explica); el dueño ve todas. La misma cantidad de días vale para los huéspedes y las reservas abiertas que ve recepción (por defecto 3: se cambia en Ajustes). En *Código* queda un aviso («Hoy llega 1 reserva») que lleva a *Reservas*.
- **Las reservas, separadas según el check-in.** En la pestaña *Reservas* de recepción y en *Más → Reservas anotadas* del dueño, la información está partida en dos secciones con su cantidad: **«Falta ingresar»** (todavía no ingresó nadie: las que están por llegar, las que ya pasaron de fecha sin check-in y las que tienen el código dado pero nadie entró todavía) y **«Ya ingresaron»** (al menos una persona hizo el check-in: primero *Faltan huéspedes*, con cuántos entraron —«Ingresaron 2 de 3 (falta 1)»— y quiénes; después *Completas*, con todos adentro). Las canceladas (solo el dueño) van aparte. A las que tienen el código dado y a las que esperan huéspedes recepción les puede volver a dar el código con *Dar código*; a las que falta ingresar se les hace el check-in como siempre. El buscador también encuentra por el nombre de quien ya ingresó. Recepción ve las que **todavía no empezaron** por la fecha de ingreso (de N días atrás a N adelante) y las que **ya empezaron** mientras su última actividad esté dentro de esos N días; el dueño ve las de los últimos 60 días. En *Código*, las «Reservas abiertas» también están separadas: *Todavía no ingresó nadie* y *Ya ingresó alguien, faltan huéspedes*. Si el dueño corrige la habitación o la cantidad de huéspedes de una reserva ya empezada, se ve lo corregido.
- **Reservas duplicadas («figura que falta llegar pero el huésped ya está»).** Pasa cuando una reserva anotada espera y, aparte, se abrió otra reserva en la misma habitación (por ejemplo una *Reserva rápida*) donde el huésped hizo el check-in: la anotada queda sola, «Todavía no llegó», para siempre. Ahora: (1) en *Faltan llegar* y *Próximas*, una anotada que tiene una reserva abierta aparte en su misma habitación (fechas hasta 5 días de diferencia) lo avisa: *«Puede que ya haya llegado: en la Hab. 202 hay una reserva con 2 huéspedes ingresados»*; (2) al abrirla, el detalle pregunta primero **«¿Esta reserva ya llegó?»**, muestra esa reserva (quién la abrió y quiénes ingresaron) y **no deja hacer el check-in ni elegir cómo paga** hasta decidir: **«Es la misma: unir»** (confirma; la anotada pasa a ser esa reserva, con su nombre y su nota, sin cambiar lo cobrado ni los huéspedes) o **«No es la misma persona: seguir con el check-in»**; (3) al abrir una *Reserva rápida* o anotar a alguien para una habitación que ya tiene una anotada esperando, avisa una vez *«La Hab. 209 ya tiene una reserva anotada a nombre de… Si es esa persona, hacé el check-in desde Faltan llegar»* (si es otra persona, a la segunda vez se crea igual). Si ya se había hecho el check-in desde la anotada y quedó una reserva vacía «con el código dado», se **anula** esa (*Anular*, vuelve la anotada) y se une con la que tiene a los huéspedes. La base rechaza unir reservas de distinta habitación, con más de 10 días de diferencia, una ya unida a otra anotada, una anulada o una anotada cancelada.
- **Número de reserva.** Cada reserva tiene su **número propio** («N.º 41»), visible en la pantalla *Reservas*, en el detalle del check-in, en la tarjeta del código, en *Huéspedes*, en *Reservas anotadas* y en la caja del dueño. Es un solo contador para todas: una reserva anotada y la reserva que sale de ella al hacer el check-in **comparten el número**; una reserva rápida (sin anotar antes) tiene el suyo. Nunca se repite ni se cambia, y una reserva eliminada y restaurada conserva el suyo. Así, la anotada de Maldonado (N.º 41) y una reserva rápida de la misma habitación (N.º 55) se ven como **dos reservas distintas**. El buscador de *Reservas* también encuentra por número («41»). Las reservas que ya existían se numeran de la más vieja a la más nueva al aplicar el SQL.
- **Dueño: eliminar y restaurar.** En cada reserva de *Reservas* el dueño tiene **Eliminar** (con confirmación que dice qué pasa). **No se borra nada**: la reserva sale de las listas y de las estadísticas y va a la pestaña **Eliminadas** (solo del dueño, últimos 60 días), con su número, quién la eliminó y cuántos huéspedes se fueron con ella; **Restaurar** la devuelve con sus huéspedes y su número. Una reserva anotada que no llegó se cancela; una reserva armada se anula (si tenía huéspedes, se van con ella). Recepción no ve «Eliminadas» ni «Eliminar» (puede *Anular* las que no tienen huéspedes). **Aparecen todas las reservas** (las anotadas por el dueño y las que recepción abrió como rápidas), en *Faltan llegar*, *Falta cerrar*, *Cerradas* e *Historial*.
- **Aviso de reservas que parecen repetidas.** Dos reservas de la misma habitación cuyas fechas se pisan (o una reserva rápida y una anotada con hasta 5 días de diferencia) avisan *«Parece repetida: la N.º 55 (Maldonado) es de la misma habitación y fechas parecidas»*, con el número de la otra; dos estadías seguidas de una noche cada una NO se marcan. Al abrir una reserva rápida o anotar a alguien en una habitación que **ya tiene una reserva abierta** (o una anotada esperando) también se avisa, con su número; a la segunda vez se crea igual (por si es otra persona).
- **Cobro, de a tres cosas:** arriba del paso *Cobro* hay una lista que se va tildando: *Elegir cómo paga · Elegir el medio de pago · Confirmar que ya cobró*; el botón de check-in se habilita con las tres.
- **El check-in es un paso a paso obligatorio.** Al tocar una reserva se abre el detalle en tres pasos, y cada uno habilita al siguiente: **1. La reserva** (la **habitación** primero; cuándo llega y sale, cuántos son, la nota; ahí no se cambia nada: para corregir hay *Corregir los datos de la reserva*, otra pantalla). **2. El cobro**, de a una cosa por vez: cuánto cobrar (la seña ya descontada) en efectivo, transferencia o dólares; la forma de pago **arranca sin elegir**; al elegirla aparece el medio de pago (ya elegido según la forma) y la confirmación **«Ya cobré…»**. Si cambia la forma o el medio, hay que volver a confirmar. Una reserva de obra social, o con la seña cubriendo todo, no pide confirmar. **3. El check-in**: un resumen de lo que se va a registrar (habitación, nombre, huéspedes y cobro) y el botón *Hacer el check-in y dar el código*, que **sigue apagado y dice qué falta** hasta que el cobro esté confirmado. Hecho el check-in, va solo a *Código* con el código. Desde ahí sigue **igual que siempre**: código, huéspedes de a uno, «Reservas abiertas», se cierra sola al entrar el último.
- **Si en el mostrador se cobró otro monto:** *Cobré otro monto* deja escribir **solo cuánto se cobró** (en la moneda de esa forma de pago; el total de la reserva pasa a ser eso más la seña ya pagada). La habitación, las noches, los huéspedes, el canal y la categoría salen tal cual de la reserva anotada: no hay un formulario libre en el check-in. Dos toques seguidos crean una sola reserva; cerrar la ventana a mitad de camino no guarda nada. Los precios se anotan para recepción, pero **lo que queda registrado es lo que se cobró de verdad**.
- **Desde la lista**, recepción también puede *Anotar una reserva (a nombre de…)* (el que llega de la calle: llega hoy, así que se abre solo el detalle para cobrarle) y *Corregir los datos de la reserva* de las que ve. La base rechaza el check-in y la corrección de una reserva fuera de esos días aunque se llame a mano.
- **Base de datos (número de reserva y «Eliminadas»):** hay que ejecutar el SQL nuevo (agrega la columna `numero` —las reservas que ya existen se numeran solas—, reemplaza 7 funciones y saca una versión vieja de `estadia_crear`; no borra ni cambia datos y se puede repetir). **Ejecutarlo ANTES de publicar las pantallas nuevas.** Sin él, las pantallas siguen andando pero sin números ni pestaña «Eliminadas». Probado: `node scripts/test-numero.mjs` (numeración sin saltos, que la anotada conserve su número al hacer el check-in, unir, eliminadas solo para el dueño y restaurar, y el pase desde la base publicada hoy, con reservas ya cargadas, aplicando el archivo dos veces).
- **Base de datos (próximas reservas y cierre de reservas):** volver a ejecutar `supabase/estadias.sql` en el SQL Editor (agrega la función `recepcion_proximas`; solo agrega, no borra nada y se puede repetir y **no toca los días que ya tenías configurados**). **Ejecutarlo ANTES de publicar la guía nueva**: sin la función, la pestaña *Reservas* muestra un error. Después, el dueño pone los días que quiera en *Ajustes*.
- **La reserva queda a nombre del titular** y con la nota: «Hab. 107 · Juan Pérez» se ve en las reservas abiertas, en *Huéspedes* y en la caja.
- **No suma en nada hasta el check-in:** una reserva anotada no es una estadía, así que no entra en ninguna estadística ni en la caja. Apenas se hace el check-in se arma la reserva con su cobro y vale lo de siempre (suma cuando entra el primer huésped).
- **Aviso de doble reserva:** si anotás una habitación cuyas fechas se pisan con otra reserva anotada de la misma habitación, avisa con quién se pisa (igual la guarda: decidís vos).
- **Cancelar** (solo el dueño) no borra: queda marcada con quién y cuándo y se restaura desde *Canceladas*. Una que ya empezó el check-in no se cancela: es una reserva con su cobro y se corrige o elimina como cualquiera. Si recepción se equivoca en el cobro y anula la reserva todavía sin huéspedes, la reserva anotada **vuelve a Reservas** para hacer el check-in bien.
- **Seña:** se carga en pesos. Si la seña se dejó en dólares, hoy se carga su equivalente en pesos.
- **Base de datos:** volver a ejecutar `supabase/estadias.sql` en el SQL Editor (agrega la tabla `private.reservas_anotadas`, las columnas `titular` y `nota` de las reservas y funciones nuevas; no borra nada y se puede repetir). **Ejecutarlo ANTES de publicar la guía nueva.**
- Pruebas: `node scripts/test-proximas.mjs` (la lista de próximas reservas: solo los días que fija el dueño —hace 7 días no se ve, hace 4 sí—, que cambiar los días cambia lo que se ve, las secciones falta ingresar / ya ingresaron (quiénes entraron, completas, el código dado sin nadie, lo corregido por el dueño y la ventana de las que ya empezaron), el orden, el límite de 300, que la base frena lo de fuera de los días y la migración desde `scripts/fixtures/estadias-v5.sql`), `node scripts/test-unir.mjs` (reservas duplicadas: unir la anotada con la reserva donde el huésped ya ingresó, el caso de la 202 de punta a punta, qué no se puede unir, que se conserva el nombre que ya tenía y la migración desde `scripts/fixtures/estadias-v7.sql`), `node scripts/test-cierre.mjs` (cerrar una reserva a mano y reabrirla —solo el dueño—, que el código deja de servir, la lista de reservas con quiénes ingresaron y su estado, la ventana de días y la migración desde `scripts/fixtures/estadias-v6.sql`), `node scripts/test-hub.mjs` (qué reserva va en cada pestaña, el historial por día y el cartel de «qué falta llegar»), `node scripts/test-buscar.mjs` (el buscador, las secciones «falta ingresar» / «ya ingresaron» y el cartel de cuántos ingresaron), `node scripts/test-llegadas.mjs` (permisos —recepción anota y corrige pero no cancela—, validaciones, ventana de 3 días, check-in con cobro en efectivo/transferencia/dólares, aviso de doble reserva, cancelar y restaurar, que no suma antes del check-in y la migración desde la versión publicada, `scripts/fixtures/estadias-v3.sql`) y `node scripts/test-cobro.mjs` (las cuentas).

## Avisos en el celular (notificaciones push)
El dueño y el personal reciben un **aviso en el celular** cuando se anota una reserva o se hace un check-in, con la app instalada en la pantalla de inicio. Sin servicios de pago ni cuentas nuevas: se usa el estándar Web Push (el que ya traen iPhone y Android), la base de Supabase y una función en Vercel.

- **Qué avisos y a quién** (a quien hizo la acción no se le avisa):
  - **Reserva anotada por el dueño** → les llega a recepción. *«Reserva nueva · Hab. 107 · Juan Pérez · llega vie 21/11 · 3 huéspedes»*.
  - **Reserva anotada por recepción** → le llega al dueño (y a quien tenga rol de dueño) y a los otros de recepción, con quién la anotó.
  - Al tocar el aviso de una **reserva nueva**, recepción abre directo la pestaña **Reservas** (para buscarla y atenderla); el dueño abre su Inicio; el aviso de **check-in** abre *Reservas* en recepción (con el código arriba).
  - **Check-in de un huésped** → le llega al dueño. *«Check-in realizado · Hab. 107 · Juan Pérez · 1 de 3 huéspedes»*, y al entrar el último, *«… · reserva completa»*. Un solo aviso por reserva: el nuevo reemplaza al anterior en vez de apilarse. Si el que dio el código fue el dueño, no se le avisa a él.
  - En *Ajustes → Avisos en los celulares* el dueño elige si el aviso lleva el **nombre del titular** (apagado: solo la habitación) y si el aviso de **check-in también le llega a recepción** (apagado por defecto).
- **Cada celular los activa una vez**: un cartel «Activá los avisos» arriba del Inicio / Código (o *Más → Avisos en este celular*) con el botón **Activar avisos**; el celular pide permiso y se registra. Hay un botón **Enviar aviso de prueba** para comprobar que llega. Cada celular queda atado a su sesión: al tocar *Salir*, o si la sesión se cierra o vence, deja de recibir; al volver a entrar se ata solo.
- **iPhone:** hace falta iOS 16.4 o más nuevo y abrir la app **desde el ícono de la pantalla de inicio** (desde Safari no se pueden activar). Si el permiso no aparece, borrar el ícono y volver a agregarlo. **Android de gama baja:** funciona con Chrome; si los avisos llegan tarde, es el ahorro de batería del celular: en *Ajustes → Batería → Chrome (o la app) → Sin restricciones*. En ambos, el modo «No molestar» los silencia y la entrega no es instantánea garantizada.
- **Privacidad:** el contenido viaja **cifrado de punta a punta** (RFC 8291): Apple, Google y Mozilla, que llevan el aviso al celular, solo ven datos ilegibles. Pero el texto **aparece en la pantalla bloqueada**. Por eso solo lleva habitación, titular (apagable), cuántos huéspedes y quién anotó: **nunca** documentos, teléfonos, emails ni montos. La cola de avisos de la base se vacía a los 3 días.
- **Cómo funciona por dentro:** en la base, al anotar una reserva o hacer un check-in (`supabase/estadias.sql`: `private.push_aviso_anotada` y `private.push_aviso_checkin`) se arma el texto y la lista de celulares y se le pide, con `pg_net`, a la función `api/push.js` (en Vercel) que lo **firme** con las claves del hotel y lo **entregue**. Un fallo al avisar **nunca frena** una reserva ni un check-in. Los celulares que ya no existen (se desinstaló la app) se sacan solos. `public/sw.js` es el «programita» del celular: muestra el aviso y abre la app al tocarlo; no guarda nada (sigue sin copia sin conexión).
- **Puesta en marcha (una sola vez, hecha por el dueño):**
  1. **Claves en Vercel** (*Project → Settings → Environment Variables*, en Production y Preview) y después **Redeploy**: `VAPID_PUBLICA`, `VAPID_PRIVADA`, `VAPID_SUBJECT` (la dirección de tu sitio, `https://…`) y `PUSH_SECRETO`. La clave **pública** ya está en `src/config.js` (`VAPID_PUBLICA`); la **privada** y el secreto **nunca** van al repositorio.
  2. **Base de datos:** ejecutar `supabase/estadias.sql` (como siempre, antes de publicar), activar la extensión **pg_net** (*Database → Extensions*) y cargar a dónde y con qué secreto se envía: `update private.push_config set url = 'https://TU-DOMINIO/api/push', secreto = 'EL-MISMO-PUSH_SECRETO' where id = 1;`.
  3. **Cada celular:** abrir la app desde el ícono, tocar **Activar avisos**, aceptar el permiso y probar con **Enviar aviso de prueba**.
  Mientras falte el paso 1 o el 2, los celulares se pueden activar pero no sale ningún aviso (la app lo dice en *Más* y en *Ajustes*).
- **Cambiar las claves** (por ejemplo si se filtran): generar un par nuevo (`node -e "const w=require('web-push');console.log(w.generateVAPIDKeys())"`), cambiar `VAPID_PRIVADA` en Vercel y `VAPID_PUBLICA` en Vercel y en `src/config.js`, y cada celular tiene que volver a tocar **Activar avisos**.
- Pruebas: `node scripts/test-avisos.mjs` (la base: a quién le llega cada aviso y a quién no, sesiones cerradas, que un fallo al avisar no frena una reserva ni un check-in, topes y limpieza, y la migración desde la versión publicada), `node scripts/test-push-api.mjs` (la función de Vercel: autenticación, validación, celulares caídos o vencidos, y firmado/cifrado con la librería real) y `node scripts/test-push-sw.mjs` (el programita del celular). La activación en el navegador (service worker, permiso, registro, aviso mostrado y abrir la pantalla correcta) se probó con Chromium y una suscripción simulada: Chromium sin interfaz no trae el servicio de avisos de Google ni se puede probar un iPhone real, así que **la entrega real en cada celular se comprueba con «Enviar aviso de prueba»**.

## Publicar (Vercel)
El proyecto de Vercel está conectado a este repo: cada cambio en `main` se publica solo. Configuración: preset **Vite**, comando `npm run build`, carpeta de salida `dist`. No hacen falta variables de entorno.

## La clave del dueño
- Se guarda en la base solo como hash (bcrypt), nunca en texto ni en el código.
- Se cambia desde el panel: **Datos generales → Clave del panel**.
- Si se pierde, se restablece desde el SQL Editor de Supabase:
  ```sql
  update private.admin set hash = extensions.crypt('clave-nueva-larga', extensions.gen_salt('bf')) where id = 1;
  ```
- Hay un freno: 8 intentos fallidos por minuto y por IP. La IP sale de lo que escriben Cloudflare y Supabase (`cf-connecting-ip` / `sb-forwarded-for`), no del `X-Forwarded-For` que manda el cliente, y las IPv6 se agrupan por /64.

## Seguridad
La URL de Supabase y la clave `publishable` van en el navegador **a propósito**: son públicas por diseño. Lo que protege los datos son las reglas de la base (`supabase/schema.sql`):
- la tabla del contenido solo se puede **leer**; escribirla directo está bloqueado;
- guardar exige la clave del dueño, valida la forma del contenido y archiva la versión anterior;
- las tablas privadas (clave, historial, intentos) no se pueden ver por la API.

Los links cargados en el panel solo se aceptan si empiezan con `http://` o `https://`.

## Rehacer la base en otro proyecto de Supabase
1. En el SQL Editor, ejecutar `supabase/schema.sql` y la línea final comentada con tu clave. Para el check-in digital, ejecutar después `supabase/checkin.sql` y, por último, `supabase/estadias.sql` (reservas y estadísticas).
2. Poner la URL y la clave publishable del proyecto nuevo en `.env` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_KEY`) o en `src/config.js`.
3. Cargar el contenido inicial: `ADMIN_PASSWORD="tu-clave" npm run seed` (usa `src/data/hotel.js`; sirve también para volver a los datos de ejemplo).
